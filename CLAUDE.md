# Blueprint Platform — Project Context for Claude Code

## What this project is

Blueprint is an Angular **project builder**, not just a component library. A developer runs a CLI (`create-blueprint-app`, not yet built) or `npx create-nx-workspace --preset=@blueprint-platform/foundation`, answers a few prompts, and gets a fully wired, production-ready Angular project: zoneless, signal-driven, themed, with a headless-first component system already in place.

There are **two separate repositories** involved:
- **`blueprint-platform`** (this repo) — an Nx workspace hosting four independently-versioned, independently-published npm packages ("pillars"). This is where generator logic lives.
- **`blueprint-reference`** (sibling repo, plain Angular CLI, no Nx) — a hand-developed sandbox app where components/theme are built and visually verified *before* being manually synced into this repo's generator templates. Never edit `blueprint-platform` generator template content without first verifying the equivalent in `blueprint-reference`, unless the content is generator-only (has no reference-app equivalent, e.g. `app.routes.ts.template`).

## The four pillars (all in this one Nx workspace, separately versioned)

| Pillar | Package | Role |
|---|---|---|
| 1. Foundation | `@blueprint-platform/foundation` | The `preset` generator — scaffolds the whole app by default. Theme tokens, config-provider, base spartan-derived UI (button, utils), routing skeleton, manifest. |
| 2. Components | `@blueprint-platform/components` | Hosts **all ~64 spartan-derived UI component sources** + the single `ui` generator that copies them (and their deps) into a generated project on demand. `foundation` depends on this and delegates the starter-set + layout-set copies to it. Bigger composite pieces (data-table, audit-log) — not yet built. |
| 3. Modules | `@blueprint-platform/modules` | On-demand generators for business domains. **`auth` generator built** (see Current status); user-management etc. — not yet built. |
| 4. Templates | `@blueprint-platform/templates` | Composite generators bundling components+modules+layout into presets like admin-dashboard — **not yet built**. |

Plus **`@blueprint-platform/generator-kit`** — not a pillar (nothing a generated project ever depends on), a plain library of shared generator-authoring helpers (`appendProvider`, `wrapRoutesUnderLayout`, `registerUiPaths`, `appendToManifest`) that `foundation`/`components`/`modules`/`templates` depend on **in their own `package.json`** to write *their* generators. **Hard rule: `generator-kit` must never appear in a generated project's `package.json`** — it's a dependency of the generator packages' own code, not of anything they produce. `preset.ts` writing to a generated project's `package.json` and `packages/foundation/package.json` itself are two completely different files; conflating them here is the easiest mistake to make.

**Versioning:** each pillar has its own independent semver line (`"projectsRelationship": "independent"` in `nx.json`'s release config — this must never be lost or accidentally reset to lockstep). `packages/foundation/compatibility.json` bundles a snapshot of which versions of the other three pillars are known-compatible with the current foundation version — this file travels with the published package, no runtime network fetch. A generated project's `.blueprint/manifest.json` records exactly which versions it was generated from.

  - **`foundation:layout` gained two options *because of* this reuse, both defaulting to the old (main-shell) behavior:** `wireRoutes` (default `true`; `false` skips the `wrapRoutesUnderLayout` sweep + welcome-index-route wiring — a content-only shell like an auth layout must never become the app's root wrapper) and `withAccountMenu` (default `true`; `false` skips adding `user-menu`/`theme-switcher`/`language-switcher` — an auth page has no signed-in user yet). `modules:auth` calls `layoutGenerator(tree, { name: 'auth-split'|'auth-centered', wireRoutes: false, withAccountMenu: false })`, then wires its own `auth` route branch via `addLayoutBranch`. `preset.ts`'s own call (`layoutGenerator(tree, { name: layout })`) is unaffected — both new options default to the behavior it already relied on.

Only `login-form.ts.template` varies with `authType` (EJS-conditional import + `inject()` of `JwtAuthService` vs `SessionAuthService`) — every other form only calls the mock backend or a validator directly, so needed no templating. (Deviation from `blueprint-reference`: its `login-form.ts` hard-injects **both** services with a `?strategy=` query-param toggle for previewing both at once side-by-side; a generated project only ever has one strategy installed, so that toggle doesn't carry over.)
  - **UI dependencies are computed, not hardcoded**, same discipline as everywhere else: a new `scanUiImports` (`packages/modules/src/generators/auth/lib/scan-ui-imports.ts`, `generator-kit`'s `ui`-copy scan generalized to walk recursively since forms live one directory deeper than a flat layout-shell folder) finds every `@blueprint-platform/ui/<name>` the copied forms actually import (`alert`, `spinner`, `card`, `button`, `field`, `input`, `input-group`, `checkbox`, …— several of these, e.g. `alert`/`spinner`/`card`, are NOT in `preset`'s `STARTER_UI` set) and calls `components:ui` with that list; `card` for the auth-split/centered shell itself is separately picked up by `foundation:layout`'s own existing `shellUiImports` scan. `packages/modules/package.json` needed a direct `@blueprint-platform/components` dependency for this (beyond the `foundation`/`generator-kit` the original task spec called for) — it's genuinely required at generator runtime, not just transitively available.

  - **Real bug this surfaced, fixed in `generator-kit` `0.1.2`: `appendProvider` used to always emit a brand-new `import { ... } from '<module>'` declaration, even when `app.config.ts` already had one for that exact module.** Since both `foundation`'s own `patch-app-config.ts` (for `apiInterceptor`) and `modules:auth` (for `jwtAuthInterceptor`/`sessionAuthInterceptor`) need `provideHttpClient`/`withInterceptors` from `@angular/common/http`, the second `appendProvider` call produced a **second** `import { provideHttpClient, withInterceptors } from '@angular/common/http'` line — a TS2300 "Duplicate identifier" compile error, only caught by an actual `nx build`, not by any of the tree-based unit tests (they never invoke the Angular/TypeScript compiler). ## Critical architecture decisions (don't relitigate these without reason)

- **Standalone + zoneless + signals only.** `provideZonelessChangeDetection()`, no Zone.js, no NgModules anywhere.
- **CDK + spartan/ui's headless "brain" layer, not a fully pre-styled UI kit.** PrimeNG is explicitly avoided — it went commercial-license-only for government/public-sector use in mid-2026, which matters given some of this developer's client work.
- **Spartan's own CSS variable naming convention is used directly** (`--primary`, `--primary-foreground`, `--background`, `--destructive`, etc. — see `spartan.ng/documentation/theming`), NOT a custom `--color-*` scheme. This means restyling a Helm component to match a new brand palette requires **zero template edits** — only redefining the variable *values* in `theme.scss`. Never reintroduce a custom naming scheme for colors.
- **Tailwind v4 is kept available in generated projects, alongside SCSS**, specifically so consuming developers can use Tailwind utilities for their own custom work outside generated components. Tailwind's `@theme inline` block in `tailwind-theme.css` maps its utility classes to the same CSS variables the SCSS token system defines — one source of truth, two consumption paths. **Tailwind and SCSS files can never `@use`/`@import` each other** — they must stay as separate entries in the `project.json` `build.options.styles` array, in this order: `src/styles/theme.scss` first, `src/styles/tailwind-theme.css` second (Tailwind's `@theme inline` only *references* variables, it doesn't define them), then `src/styles.scss` last (Nx's default global stylesheet, kept so app-level overrides win). `patch-app-config.ts` writes exactly these three. Global hand-authored helper classes (e.g. `.bp-field--floating`) go in `src/styles/_utilities.scss`, which `theme.scss` `@use`s — that partial is the "global class registry".
- **Copy-based generation, not npm-dependency-based, for anything a developer should be able to freely modify.** `@angular/cdk`, `@spartan-ng/brain`, `class-variance-authority`, `clsx`, `tailwind-merge`, `@ng-icons/core`, `@ng-icons/lucide`, `embla-carousel`, `embla-carousel-angular`, `ngx-scrollbar` are real pinned npm dependencies (never copied, never modified) — the last five back specific pieces of the synced UI kit / layout shells. Everything under `shared/ui/`, `shared/components/`, `features/`, `layout/` is copied source the developer owns outright.
- **Flattened/standalone project layout** — generated projects use `rootProject: true` (app lives at the workspace root, no `apps/<name>/` nesting), matching what a plain `ng new` user expects, not Nx's default multi-project nesting.

## Generator conventions

- File is named `preset.ts` (or `<generator-name>.ts`), **not** `generator.ts` — matches what `@nx/plugin:generator` actually scaffolds.
- `app.config.ts` in the generated project is edited with `ts-morph` AST manipulation (`preset/lib/patch-app-config.ts`) — never plain string replacement, since exact file shape shifts across Angular/Nx versions. Structured JSON files (`tsconfig.json` `paths`, `project.json` `targets.build.options.styles`, generated `package.json` deps) are edited with `@nx/devkit`'s `updateJson`, not string replacement either.
- **Routing composition lives in its own helper (`generator-kit`'s `wrapRoutesUnderLayout`), separate from `patch-app-config.ts`** — providers/imports vs. route-tree shape are distinct concerns. It also uses `ts-morph` (wrap `routes[]` as `children` of a lazy-loaded shell route, with an optional `indexRoute` child), never string replacement. A shell component's exported class name is **read from its own copied source** (`export class …` match), not derived from the `layout` value — same principle as computing UI paths/deps from what's actually in the `files/` tree.
- **`layout` enum values carry the `-shell` suffix** (`sidebar-shell`, not `sidebar`) and equal the folder name under `files/layout/` and in the generated `src/app/layout/`; the shell entry file is `<layout>/<layout>.ts`. Don't re-append `-shell` in path construction.
- **`project.json`, not `angular.json`**, holds the `styles` array in Nx-generated Angular apps — there is no workspace-wide `angular.json` in this setup. (This was a real bug hit and fixed mid-project — don't reintroduce the `angular.json` assumption.)
- `compatibility.json` is read via `readFileSync`/`JSON.parse` at generator runtime, **not** via a static `import * as compatibility from '...json'` — the static-import form produced inconsistent interop behavior (values resolving to `undefined`) under this workspace's `module: nodenext` config.
- Any folder under a generator's `files/` directory containing real `.ts` source (meant to be copied verbatim, not compiled) must be excluded from `tsconfig.lib.json`'s compilation (`"exclude": ["src/generators/**/files/**/*"]`) and instead copied via an explicit `assets` glob rule in the package's `nx.targets.build.options.assets` array. Forgetting either half of this causes either TS compile errors (trying to resolve spartan/cva/clsx imports that aren't foundation's own dependencies) or missing files in `dist`.
- **Never let a manually-created `project.json` coexist with `package.json`-based inferred Nx configuration for the same pillar package.** This caused a real, hard-to-diagnose bug: a stale `project.json` created early in the project silently overrode every subsequent edit to `package.json`'s `nx.targets.build.options.assets`, for a long stretch of debugging. If a pillar ever behaves as if config edits aren't taking effect, check for a stray `project.json` first.
- TypeScript path entries (`compilerOptions.paths`) for UI components are **generated programmatically** — the `@blueprint-platform/components:ui` generator writes one `@blueprint-platform/ui/<name>` entry per component it copies (except the flat family). Never hardcode a per-component path list. `preset.ts` no longer touches UI paths at all; it delegates the whole starter-set + layout-set copy (files, paths, npm deps) to that generator.
- **UI-component npm deps are computed, not hardcoded in `preset.ts`.** `ui`'s `lib/npm-deps.ts` scans each copied component's real `from '…'` specifiers and adds only the matching packages. `preset.ts` keeps just `@angular/cdk` + the Tailwind toolchain. Adding a component that needs a new package means updating the `UI_NPM_DEPS` map + `SPECIFIER_TO_PKG` in `lib/npm-deps.ts`, nowhere else.
- **`apiUrl` / `environment.apiUrl` is an origin ONLY — never a path.** `preset.ts`'s `toOrigin()` strips any path/trailing slash before it reaches `environment.ts` or `proxy.config.json`. Reason: Orval generates service methods whose paths already start with `/api/...` (from the backend's own route templates), and `api.interceptor.ts` prefixes `API_URL` onto every root-relative request — so `apiUrl` ending in `/api` yields `/api/api/...`. Do not "fix" this by putting the path back; if a specific backend's OpenAPI paths genuinely lack the `/api` prefix, that's a per-project interceptor/proxy adjustment, not a change to the origin-only rule.
- **Orval config reads the plain `environment` module, not the `API_URL` token.** `orval.config.ts` runs in Node before any Angular app exists — an `InjectionToken` is meaningless there. Both read the same `src/environments/environment.ts` value, which is the actual single-source-of-truth guarantee.
- **Text direction follows the language registry, never a per-code conditional.** `lib/language-registry.ts` (`code → { label, dir }`) is the compile-time canonical source; `preset.ts` validates `--languages` against it and *renders* the generated project's identical `core/language/language-registry.ts` from it (so they can't drift). Adding a language = one registry entry. Never write `if (code === 'ar')` anywhere — `LANGUAGE_REGISTRY[code].dir` is the answer for every language, present and future.
- **Placeholder i18n files.** Only `files/i18n/en.json` + `ar.json` are real. Any other requested `--languages` code is generated as English content with a leading `"_note"` JSON key flagging it needs real translation (JSON has no comments — a key is the substitute). `en`/`ar` never get the `_note` key.
- **Split gating for optional subsystems.** The translation *engine* (service, registry, i18n assets, providers, deps, the `Directionality` alias) is gated on `showLanguageSwitcher` alone — independent of `layout`. The pre-built `language-switcher` UI needs both `showLanguageSwitcher` and a `layout` to live in — but note as of `foundation:layout` (below), the `layout` generator itself has no `showLanguageSwitcher` option; it infers the switcher decision from whether `core/language/` already exists in the target tree. `patch-user-menu.ts` reconciles `user-menu`'s hard import of `LanguageSwitcher` when the switcher isn't generated.
- **Generator-authoring logic shared across pillars belongs in `@blueprint-platform/generator-kit`, not copy-pasted.** Before writing another "read a file, ts-morph it, write it back" or "read/ensure-array/push/write JSON" helper, check whether `appendProvider` / `wrapRoutesUnderLayout` / `registerUiPaths` / `appendToManifest` already covers it — and if the pattern you're generalizing has *moved* since a task description was written (e.g. UI tsconfig-path writing moved from `foundation` into `components:ui` in an earlier task), generalize it where it actually lives now, not where an older doc assumed it still was.
- **A standalone on-demand generator that mirrors a `preset.ts` generation-time option must not need options `preset.ts` didn't pass it.** `foundation:layout` only takes `{ name }` — it recovers the rest (e.g. whether to include `language-switcher`) by inspecting the target tree's actual current state, the same discipline `patch-user-menu.ts` already used. This is also why `preset.ts` calling `layoutGenerator(tree, { name: layout })` reproduces its old inline behavior exactly: by the time that call happens, every earlier preset step it depends on (the translation engine, if any) has already run.
- **Never let a generator delete its own package from a generated project's `package.json` if any of its *other* generators are meant to be runnable against that project later.** `preset.ts` used to delete `@blueprint-platform/foundation` outright; that silently broke `foundation:layout` before it existed to expose the bug. It's now kept as a devDependency (version read from foundation's own `package.json`, not `compatibility.json`'s stale self-entry), same as `components`.
- **Calling another pillar's generator function in-process (not just its templates) needs an explicit deep `exports` entry on the target package** — e.g. `foundation`'s `"./generators/layout"` (mirroring `components`'s `"./generators/ui"`), each with an `@blueprint-platform/source` condition (dev/test), `types`, `require`, and `default`. Node's `exports` field is a strict allowlist once present; `require('@scope/pkg/dist/generators/x/x')` from another published package is rejected without one. The calling package gets a small local shim in its own `generators/shared/` (`loadXGenerator()`, try/catch `require(...)`) — same shape every time, don't inline the `require` at the call site.
- **A generator that composes into another pillar's generator, adding a *sibling* route branch rather than the main app shell, must register that branch as protected** (`generator-kit`'s `addLayoutBranch`, which writes `.blueprint/manifest.json`'s `protectedRouteBranches`) instead of using `wrapRoutesUnderLayout` for its own routing. `wrapRoutesUnderLayout` sweeps every existing top-level route into a new main shell's children — correct for the one main shell, wrong for a branch (e.g. `modules:auth`'s `auth`) that must stay a sibling regardless of when a main shell is added. This is also why reusing `foundation:layout` wholesale for a content-only shell is wrong without its `wireRoutes: false` / `withAccountMenu: false` options — those exist specifically so a shell like `auth-split`/`auth-centered` doesn't accidentally become the app's root wrapper or grow an account menu for a page with no signed-in user.

## Registry / publishing conventions

- Real registry: **npm public registry**, scope `@blueprint-platform` (chosen because `@blueprint` itself may not have been available as an npm org — confirm before assuming).
- Local testing registry: Verdaccio (`npx verdaccio`, `http://localhost:4873`).
- **Critical gotcha:** if `.npmrc` (project-local or global `~/.npmrc`) has a scope-specific registry mapping (`@blueprint-platform:registry=...`), it silently overrides any `--registry=` flag passed to `npm publish`/`npm dist-tag`/`create-nx-workspace` for that scope. Use the scoped-override flag form instead when testing locally: `npm publish --@blueprint-platform:registry=http://localhost:4873`. Remember to point the scope back at the real npm registry once local testing is done.
- Two dist-tags drive version resolution: `latest` (bleeding edge) and `stable` (tested-as-a-set, gated by manually updating `compatibility.json`). The CLI (once built) should resolve `stable` by default, never resolve an embedded version string directly in `--preset=@scope/pkg@x.y.z` — this is unreliable on current Nx for scoped packages (known upstream bug, Nx issue #23174) and should always go through a dist-tag instead.
- `package.json` for a publishable pillar needs: `"generators": "./generators.json"` (top-level field, easy to forget), an `exports` entry for `./generators.json` specifically (Node's `exports` is a strict allowlist), and a `"files"` array including `dist`, `generators.json`, and `compatibility.json` (otherwise `.gitignore`-based default packing may silently exclude `dist/`).

## Workflow discipline (from the governance doc, still applies)

- `blueprint-reference` folder structure mirrors the pillar targets 1:1 (`src/app/ui/button/` ↔ `packages/components/src/generators/ui/files/shared/ui/button/` — UI kit now lives in the components pillar, not foundation) specifically so syncing is mechanical, not a judgment call.
- A piece is "sync-ready" only when: it uses only spartan/theme CSS variables (no hardcoded colors), has no console errors, works in both RTL and LTR if layout-sensitive, and the brain/behavior layer is provably untouched from spartan's original.
- Every sync gets a `SYNC_LOG.md` entry and a git tag (`sync/<name>/<version>`) in `blueprint-reference`, recording exactly which reference-app commit backs which published pillar version.
