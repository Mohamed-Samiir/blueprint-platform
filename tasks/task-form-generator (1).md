# Task List: `modules:form` Generator

## Context

`blueprint-platform` needs a new generator, `modules:form`, that scaffolds a
form component from a developer-authored model file. The developer places a
`bp.models/<model-name>.ts` file in their generated project (this is a plain
export of an array of field descriptors — it is NOT generated by us, it is
authored by the app developer). The generator statically reads that file,
picks the right render function for each field's `type` from
`field-renderers.ts`, and writes out a `<name>.html` / `<name>.ts` /
`<name>.scss` component.

Confirmed scope constraints (from the user, do not deviate):

- **Superseded by Task 8, read that task before touching validators or
  errors:** the original constraint here was that `field-renderers.ts`
  emits no validators and no error-message blocks, and is copied in
  as-is with zero edits. The user has since asked for inline error
  rendering *embedded inside each field's own markup block*, which
  requires a small, deliberate edit to `field-renderers.ts` (an added
  `errorHtml` parameter per render function — see Task 8). That edit is
  the one sanctioned exception to "copied as-is." Everything else in
  this constraint still holds: no dynamic option binding, no validator
  logic living inside the renderer functions themselves (they only
  splice in a pre-built error string — they still don't decide what
  validators apply or compute error text), and no execution of the
  developer's model file.
- `select` / `selectMultiple` / `combobox` / `comboboxMultiple` /
  `radioGroup` render functions still emit **static placeholder options**
  ("Option 1", "Option 2", "Option 3"). This is intentional — the developer
  wires up a real data source themselves after generation. Do not add
  dynamic option binding, inputs for option sources, or TODO-removal logic.
- The model is read **statically** (via `ts-morph` AST parsing of the
  source file), never via `require()`/dynamic `import()`/`eval` of the
  developer's file. This is a deliberate safety choice — do not "simplify"
  this later to a runtime `require`.
- **`'button'` is a real, user-placed field type (Task 9), not a
  showcase-only renderer** — an earlier version of this task list
  excluded it on that assumption; that's reversed. A button entry sits in
  the same `bp.models` array as ordinary fields, wherever the developer
  wants it, but it isn't form-control-backed: no `formControlName`, no
  validators. It carries a `handler` (the name of a click-handler method
  the generator stubs out on the generated component — the developer
  fills in the body) and a `variant` (`'primary' | 'secondary' |
  'outline' | 'ghost'`).

`field-renderers.ts` (already authored by the user) is copied into this
generator's `lib/` folder with only two sanctioned edits applied — no
other changes: the Task 8 `errorHtml` parameter added to the 15 control
render functions, and the Task 9 signature change to `button` so it
renders one real, wired-up button instead of its original showcase
content. It exports a `PilotFieldConfig` interface, a `gridSpanClass()`
helper, and 16 functions: `textInput`, `numberInput`, `timePicker`,
`select`, `selectMultiple`, `combobox`, `comboboxMultiple`, `datePicker`,
`dateRangePicker`, `inputOtp`, `attachment`, `radioGroup`, `slider`,
`switchToggle`, `checkbox`, `button`.

## Task 1 — `FieldType` union and `FieldModelEntry` interface

Create `packages/modules/src/generators/form/lib/field-model.types.ts`.

1. Define and export:

   ```ts
   export type FieldType =
     | 'textInput'
     | 'numberInput'
     | 'timePicker'
     | 'select'
     | 'selectMultiple'
     | 'combobox'
     | 'comboboxMultiple'
     | 'datePicker'
     | 'dateRangePicker'
     | 'inputOtp'
     | 'attachment'
     | 'radioGroup'
     | 'slider'
     | 'switchToggle'
     | 'checkbox'
     | 'button';
   ```

   Note: this is 16 entries, matching all 16 functions in
   `field-renderers.ts`. **Revision:** an earlier version of this task
   list excluded `'button'` on the assumption it was a showcase-only
   renderer. The user has since asked for it as a real, user-placed field
   type — a button the developer positions in the model like any other
   field, with its own click handler and visual variant. `'button'` is a
   genuinely different *kind* of entry, though (not form-control-backed,
   no validators) — see Task 1.2 for how `FieldModelEntry` accounts for
   that, and Task 9 for the parsing/generation/rendering work it needs.

2. Define `FieldModelEntry` as a **discriminated union keyed by `type`**,
   not a single flat interface — different field types accept different
   validators (a `checkbox` has no `pattern`, a `textInput` has no `min`),
   and a flat "everything optional" shape would let a developer write
   nonsense combinations with no compile-time signal. Build it in layers:

   a) `'button'` isn't form-control-backed (no `formControlName`, no
      validators), so split the base shape in two rather than forcing
      every field — including buttons — through one interface with
      properties that don't apply to it:

      ```ts
      interface BaseEntryLayout {
        label: string;
        colSpan?: number;
        colSpanSm?: number;
        colSpanMd?: number;
      }

      interface BaseControlEntry extends BaseEntryLayout {
        formControlName: string;
      }
      ```

      Match `BaseControlEntry` against `PilotFieldConfig` in
      `field-renderers.ts` exactly (read that file first — don't guess
      field names/optionality; `BaseControlEntry` minus `type`/
      `validators` is passed straight through as the `PilotFieldConfig`
      arg to whichever render function is selected). `label` for a button
      is its button text, which is why it stays on the shared
      `BaseEntryLayout` rather than being redefined per variant.

   b) A small family of validator interfaces, one per group of field
      types that share the same *kind* of constraint — not one per field
      type (that would be 15 near-duplicates) and not one flat interface
      (that loses the type-safety). A base validator every field can use:

      ```ts
      interface BaseValidators {
        required?: boolean | string; // true, or a custom message
      }
      ```

      and family interfaces extending it:

      ```ts
      // textInput, inputOtp
      export interface TextValidators extends BaseValidators {
        minLength?: number | { value: number; message?: string };
        maxLength?: number | { value: number; message?: string };
        pattern?: string | { value: string; message?: string };
        email?: boolean | string;
      }

      // numberInput, slider
      export interface NumericValidators extends BaseValidators {
        min?: number | { value: number; message?: string };
        max?: number | { value: number; message?: string };
      }

      // datePicker, timePicker
      export interface DateValidators extends BaseValidators {
        minDate?: string | { value: string; message?: string };
        maxDate?: string | { value: string; message?: string };
      }

      // dateRangePicker
      export interface DateRangeValidators extends BaseValidators {
        minDate?: string | { value: string; message?: string };
        maxDate?: string | { value: string; message?: string };
        minRangeDays?: number | { value: number; message?: string };
        maxRangeDays?: number | { value: number; message?: string };
      }

      // select, combobox, radioGroup
      export interface SingleSelectionValidators extends BaseValidators {}

      // selectMultiple, comboboxMultiple
      export interface MultiSelectionValidators extends BaseValidators {
        minSelected?: number | { value: number; message?: string };
        maxSelected?: number | { value: number; message?: string };
      }

      // switchToggle, checkbox — deliberately does NOT extend
      // BaseValidators: "required" is meaningless for a boolean control,
      // the real constraint is "must be true"
      export interface ToggleValidators {
        requiredTrue?: boolean | string;
      }

      // attachment
      export interface AttachmentValidators extends BaseValidators {
        maxFileSizeMb?: number | { value: number; message?: string };
        allowedExtensions?: string[] | { value: string[]; message?: string };
        maxFiles?: number | { value: number; message?: string };
      }
      ```

      Naming rule: keep validator key names **disjoint in meaning across
      families** (`min`/`max` always mean numeric bounds, `minDate`/
      `maxDate` always mean date bounds, `minSelected`/`maxSelected`
      always mean selection-count bounds). This lets Task 8.3's default
      error-message table stay a single flat lookup keyed by validator
      name, with no ambiguity about which family a key belongs to.

   c) A map from `FieldType` to its validators interface — deliberately
      covers only the 15 control types, **not** `'button'`, since a
      button has no validators concept at all:

      ```ts
      export interface FieldValidatorsMap {
        textInput: TextValidators;
        inputOtp: TextValidators;
        numberInput: NumericValidators;
        slider: NumericValidators;
        datePicker: DateValidators;
        timePicker: DateValidators;
        dateRangePicker: DateRangeValidators;
        select: SingleSelectionValidators;
        combobox: SingleSelectionValidators;
        radioGroup: SingleSelectionValidators;
        selectMultiple: MultiSelectionValidators;
        comboboxMultiple: MultiSelectionValidators;
        switchToggle: ToggleValidators;
        checkbox: ToggleValidators;
        attachment: AttachmentValidators;
      }

      export type ControlFieldType = Exclude<FieldType, 'button'>;
      ```

   d) The button variant itself — a plain interface, not part of the
      mapped-type machinery in (e), since it doesn't fit the
      control-plus-validators shape at all:

      ```ts
      export type ButtonVariant = 'primary' | 'secondary' | 'outline' | 'ghost';

      export interface ButtonFieldEntry extends BaseEntryLayout {
        type: 'button';
        /**
         * Name of the click-handler method the generator will stub out
         * on the generated component class. The developer implements the
         * body themselves after generation — this is a name, not code,
         * and is never executed by the generator (see Task 9.1).
         */
        handler: string;
        /** Defaults to 'primary' when omitted. */
        variant?: ButtonVariant;
      }
      ```

   e) The discriminated union itself, assembled from (a)–(d) via a mapped
      type over the 15 control types, unioned with `ButtonFieldEntry` so
      it stays in sync automatically as `FieldType` grows:

      ```ts
      export type FieldModelEntry =
        | {
            [K in ControlFieldType]: BaseControlEntry & {
              type: K;
              validators?: FieldValidatorsMap[K];
            };
          }[ControlFieldType]
        | ButtonFieldEntry;
      ```

      With this shape, once a developer's object literal has `type:
      'checkbox'`, TypeScript narrows `validators` to `ToggleValidators`
      and rejects `pattern`/`min`/etc. at compile time in their own
      project; a `type: 'button'` entry narrows to `ButtonFieldEntry` and
      TypeScript rejects `formControlName`/`validators` on it entirely —
      this is a real authoring-time safety net, not just documentation.

   f) **Runtime companion, not just a type.** `ts-morph` reads the AST,
      not compiled types — a developer could still hand-write an invalid
      combination (or bypass their editor's type-checking) and run the
      generator directly. So Task 2's parser needs an actual runtime
      allow-list mirroring `FieldValidatorsMap`, e.g.:

      ```ts
      export const VALID_VALIDATOR_KEYS: Record<ControlFieldType, readonly string[]> = {
        textInput: ['required', 'minLength', 'maxLength', 'pattern', 'email'],
        inputOtp: ['required', 'minLength', 'maxLength', 'pattern', 'email'],
        numberInput: ['required', 'min', 'max'],
        slider: ['required', 'min', 'max'],
        datePicker: ['required', 'minDate', 'maxDate'],
        timePicker: ['required', 'minDate', 'maxDate'],
        dateRangePicker: ['required', 'minDate', 'maxDate', 'minRangeDays', 'maxRangeDays'],
        select: ['required'],
        combobox: ['required'],
        radioGroup: ['required'],
        selectMultiple: ['required', 'minSelected', 'maxSelected'],
        comboboxMultiple: ['required', 'minSelected', 'maxSelected'],
        switchToggle: ['requiredTrue'],
        checkbox: ['requiredTrue'],
        attachment: ['required', 'maxFileSizeMb', 'allowedExtensions', 'maxFiles'],
      };
      ```

      Put this right next to the interfaces with a comment stating both
      must be updated together, since TypeScript can't check that a
      hand-maintained `Record` of string literals stays in sync with a
      hand-maintained set of interfaces — that sync is a manual discipline
      point, flag it clearly in the code comment rather than assuming
      future edits will remember it.

3. This file (and its exported types) is meant to be **consumed by app
   developers** authoring their own `bp.models/<name>.ts` files, so:
   - Write clear TSDoc comments on the union, `BaseControlEntry`,
     `ButtonFieldEntry`, and each validator interface.
   - Add a short usage example in a comment showing a `bp.models/user.ts`
     file: `export const fields: FieldModelEntry[] = [...]`, including at
     least one `{ type: 'button', handler: 'onSave', variant: 'primary' }`
     entry alongside ordinary control fields, so developers see buttons
     are placed in the same array, not configured separately.
   - Confirm (Task 6) that this file ends up importable by generated
     projects — i.e. it must be exported from `packages/modules`'s public
     entry point, not left as an internal-only lib file, since developers
     need to `import type { FieldModelEntry, ButtonVariant } from '@blueprint-platform/modules'`
     (or whatever the package's actual public import path is — confirm
     against existing exports in `packages/modules/src/index.ts`).

## Task 2 — Static model parser (`parseFieldModel`)

Create `packages/modules/src/generators/form/lib/parse-model.ts`.

1. Export a function:

   ```ts
   export function parseFieldModel(filePath: string): FieldModelEntry[]
   ```

2. Implementation notes:
   - Use `ts-morph`'s `Project` to load the file **from disk by path**
     (this file is a pre-existing developer file already sitting in the
     generated project's source tree — it is not part of this generator's
     own Tree writes, so read it directly, not via the Nx `Tree` API).
   - Find the exported array-literal variable (e.g. `export const fields =
     [...]` or `export const <anything> : FieldModelEntry[] = [...]` — do
     not hardcode the variable name `fields`; instead find the first
     exported `VariableStatement` whose initializer is an `ArrayLiteralExpression`,
     and use that. If more than one qualifying export exists, throw a clear
     error naming the file and asking for exactly one exported array).
   - For each element (expected to be an `ObjectLiteralExpression`), read
     `type` first — everything else about how to validate that element
     branches on it.
   - Validate `type` against the `FieldType` union from Task 1 (now 16
     values, including `'button'`). Throw a clear error identifying the
     offending field's index and listing the valid types if it isn't one
     of them.
   - **If `type` is `'button'`** (see Task 9.1 for the full spec):
     statically read `label`, `handler`, and optional `variant`,
     `colSpan`/`colSpanSm`/`colSpanMd` as literals. Throw a clear error
     naming the field's index if `formControlName` or `validators` is
     present — those don't apply to a button and their presence almost
     always means the developer meant a different `type`. Validate
     `variant` against `ButtonVariant` if given. Validate `handler` is a
     non-empty string matching a safe identifier pattern (see Task 9.1
     for the exact rule) — it becomes a generated method name and a
     template click binding, so it can't contain arbitrary characters.
   - **Otherwise** (one of the 15 control types): statically read the
     property values (`formControlName`, `label`, `colSpan`, `colSpanSm`,
     `colSpanMd`) as literals. Do not evaluate expressions, spreads,
     computed keys, or function calls in the object literal — if
     encountered, throw a clear error naming the field index and the
     unsupported construct.
     - If the element has a `validators` property, read it as a nested
       object literal with the same literal-only rule, then check every
       key it contains against `VALID_VALIDATOR_KEYS[type]` (Task 1.2.f)
       — `type` is already known at this point, since the allow-list is
       looked up by it. Throw a clear error naming the field's
       index/`formControlName`, the invalid key, its `type`, and the keys
       that *are* valid for that type, if any key isn't in the allow-list
       (e.g. `pattern` on a `checkbox`, or `min` on a `textInput`). Each
       validator value itself must also match one of the two accepted
       shapes (`boolean | string | number` for a bare value, or
       `{ value: ..., message?: string }` for a value with a custom
       message) — throw a clear error naming the offending key if a value
       doesn't match either shape.
   - Throw a clear, actionable error if the file doesn't exist at all
     (distinct message from "no qualifying export found").
   - Return `FieldModelEntry[]`.

3. **Before Task 3 depends on this**, hand-write and run a few isolated
   test cases (not necessarily formal unit tests if the package doesn't
   have a test runner wired up yet — but at minimum manually exercise):
   - A valid file with 5+ different field types → correct array back.
   - A file with an unknown `type` value → clear thrown error.
   - A file with no exported array → clear thrown error.
   - A nonexistent file path → clear thrown error.
   - A file whose array uses a spread or a function call for one element
     → clear thrown error naming the unsupported construct.
   - A file with a `validators` key that's invalid for its field's type
     (e.g. `pattern` on a `checkbox`, `min` on a `textInput`) → clear
     thrown error naming the field, the bad key, and the valid keys for
     that type.
   - A file with every validator kind used correctly across a mix of
     field types (one per family: text, numeric, date, date-range,
     single-selection, multi-selection, toggle, attachment) → correct
     array back, `validators` populated per field.
   - A file with a `{ type: 'button', ... }` entry mixed in among control
     fields → correct array back, button entry has no `validators` key at
     all (not even `undefined`-valued) and its own `handler`/`variant`
     read correctly.
   - A file with a button entry that also sets `formControlName` or
     `validators` → clear thrown error.
   - A file with a button entry whose `handler` isn't a safe identifier
     (e.g. contains spaces or parens) → clear thrown error.

   Do not proceed to Task 3 until all ten behave as expected.

## Task 3 — The `form` generator itself

Create `packages/modules/src/generators/form/form.ts` (plus
`schema.json` / `schema.d.ts` per the convention confirmed in Task 0).

1. Schema options:
   - `name` (string, required) — the form name; drives
     `<name>.html`/`<name>.ts`/`<name>.scss` and the component class/selector.
   - `model` (string, required) — path to the `bp.models/<model-name>.ts`
     file, relative to the generated project's root (resolve it against
     `tree.root` + the given relative path when reading from disk for
     `parseFieldModel`, since that file is read directly rather than via
     `Tree`).
   - `directory` (string, optional) — the destination path for the
     generated component **inside the generated project**, e.g.
     `features/<module>/<name>.form`. This is a genuine addition on top of
     what `auth`/`rbac` do with `directory` (those place a whole
     feature/page tree; this one places a single reusable component), so
     don't just copy their resolution logic blindly — confirm it still
     makes sense for a single-component output, then mirror whatever
     parts do apply (e.g. how a leading `/` or `src/app`-relative path is
     normalized).
     - Treat the value as relative to the generated project's source root
       (the same root other `modules:*` generators resolve `directory`
       against — confirm the exact base via Task 0's discovery, e.g.
       `apps/<app>/src/app/` vs. the project root).
     - The path is the **folder** the component's three files go into —
       it is not itself a filename. So `--directory=features/orders`
       with `--name=order-form` produces
       `features/orders/order-form/order-form.ts` (plus `.html`/`.scss`),
       following whatever per-component subfolder convention Task 0.4
       confirmed (a `<name>/` subfolder vs. flat files in `directory`).
     - If the path segments (e.g. `features/<module>/`) don't exist yet
       in the target project, create them — Nx's `generateFiles`/`Tree`
       APIs create intermediate directories automatically when writing a
       file at a nested path, so no separate mkdir step should be needed;
       just confirm this behavior rather than assuming it.
     - Default when `directory` is omitted: mirror whatever default root
       other `modules:*` generators fall back to (confirm in Task 0) so
       `form` behaves consistently with its siblings when no destination
       is given.
     - Do not conflate this with the `.form` naming style mentioned by
       the user (`<name>.form`) — that reads as a *folder-name suffix*
       convention some teams use for feature folders, not a required
       behavior of the generator itself. The generator should accept
       whatever `directory` string it's given verbatim (so a caller who
       wants `features/orders/order-form.form/` can pass that literal
       path) rather than silently appending `.form` to every output
       folder. If the user later confirms `.form` should be
       auto-appended to the generated folder name, that's a follow-up
       change to this option's resolution logic, not something to guess
       at now.

2. Generator logic:
   - Call `parseFieldModel(resolvedModelPath)` to get `FieldModelEntry[]`.
   - **Rendering dispatch is a `renderField()` function, not a homogeneous
     `Record<FieldType, Fn>` map.** A flat `Record` needs one function
     type for all 16 entries, but `button`'s config (`ButtonFieldEntry`)
     and call convention (no `errorHtml`) genuinely differ from the 15
     control renderers (`PilotFieldConfig` + `errorHtml`). Forcing both
     into one signature means loosening the types until the map stops
     catching mistakes — the opposite of the point. Instead, write:

     ```ts
     function renderField(entry: FieldModelEntry, errorHtml: string): string {
       switch (entry.type) {
         case 'textInput': return textInput(entry, errorHtml);
         // ...the other 14 control cases...
         case 'button': return button(entry); // no errorHtml — see Task 9.2
         default: {
           const _exhaustive: never = entry;
           throw new Error(`Unhandled field type: ${(_exhaustive as FieldModelEntry).type}`);
         }
       }
     }
     ```

     The `never`-typed `default` branch is what replaces the old
     `Record`'s compile-time safety net: adding a 17th `FieldType` later
     without a matching `case` becomes a compile error here, exactly as
     the `Record` approach intended, without forcing every renderer
     through one artificial shared signature.
   - For each entry in the parsed model, call `renderField(entry,
     errorHtml)` (Task 8.4 builds `errorHtml` for control entries;
     pass `''` for button entries, it's unused) and collect the returned
     HTML strings in order.
   - Join the collected HTML into a single `fieldsHtml` string (with
     sensible separating whitespace/newlines so the output `.html` file
     stays human-readable/diffable, not one giant line).
   - Determine which imports the generated `.ts` component actually needs:
     - Only include Angular/Spartan imports for field types **actually
       present** in this specific model — do not blanket-import all 16
       renderers' worth of directives/components into every generated
       form regardless of use. Build this from the same field-type set
       used in `renderField`'s dispatch, mapping each used `FieldType` to
       its required import(s) (confirm the exact import specifiers by
       reading what markup each render function emits in
       `field-renderers.ts` — e.g. `hlm-select` needs its directive
       imports, `brn-slider` needs its own, etc.). A model using `button`
       needs whatever `HlmButton`/`BrnButton` imports Task 9.2's rewritten
       `button` function requires — include those only when a button
       entry is actually present, same rule as every other field type.
   - Use `generateFiles` with an EJS template for `<name>.ts` (component
     class boilerplate + computed imports list) and write `fieldsHtml`
     directly into the `<name>.html` output (either via `tree.write` after
     `generateFiles` runs, or via an EJS variable substitution — pick
     whichever this workspace's existing generators already do for
     "one big pre-computed string dropped into a template" and match it).
   - `<name>.scss` can be a minimal/empty starter file matching whatever
     other generated components in this workspace use as their SCSS
     starter (check an existing generated component for the convention —
     don't invent a new one).
   - **Generate one handler-stub method per unique `handler` name** found
     across all `button` entries in the model (see Task 9.3) and add them
     to the `<name>.ts` component class alongside the `FormGroup` and
     other boilerplate.

## Task 8 — Validators and inline error rendering

### 8.1 — Declarative, per-field-type validators (already defined in Task 1)

Passing actual `Validators.required` / `Validators.minLength(5)` etc. from
a `bp.models` file isn't compatible with how the model is parsed: Task 2's
parser reads only literal values from the AST and explicitly throws on
call expressions / property-access expressions on imported identifiers.
Recognizing `Validators.*` shapes safely would mean teaching the parser a
whitelisted-expression grammar — a materially bigger, riskier change than
this generator's parsing story was designed for. Use a plain declarative
config instead, built entirely from primitives the existing parser
already knows how to read.

The types for this — `BaseValidators`, the per-family interfaces
(`TextValidators`, `NumericValidators`, `DateValidators`,
`DateRangeValidators`, `SingleSelectionValidators`,
`MultiSelectionValidators`, `ToggleValidators`, `AttachmentValidators`),
`FieldValidatorsMap`, the discriminated `FieldModelEntry` union, and the
runtime `VALID_VALIDATOR_KEYS` allow-list — are all defined in **Task
1.2**, since different field types genuinely accept different validators
(a `checkbox` has no `pattern`, a `textInput` has no `min`) and that had
to be designed into `FieldModelEntry`'s shape from the start, not bolted
on separately here. Task 2's parser validation against
`VALID_VALIDATOR_KEYS[type]` is likewise already specified there. Nothing
further to add in this subtask beyond cross-referencing it — don't
redefine a second, flatter validator type here.

Custom (non-built-in) validator functions are explicitly out of scope for
this task — flagged as a v2 idea in Further Recommendations below, not
something to half-implement here.

### 8.2 — `field-renderers.ts` signature change (the one sanctioned edit)

This is the one deliberate deviation from "copied as-is." The design
requirement driving it: error markup must live **inside** each field's own
rendered block (next to that field's control), not appended after the
whole form's markup — so the render functions themselves need a seam to
receive it.

For each of the 15 field render functions (everything except `button`,
which stays untouched since it's not a real field type):

1. Add a second parameter with a safe default:

   ```ts
   export function textInput(config: PilotFieldConfig, errorHtml: string = ''): string {
     return `
       <div class="...">
         ...existing control markup...
         ${errorHtml}
       </div>
     `;
   }
   ```

2. For each function, find the correct insertion point inside its own
   returned template literal — this is **not uniform across all 15**,
   since each renderer's wrapper markup differs (e.g. `select`'s wrapper
   vs. `dateRangePicker`'s two-input wrapper vs. `attachment`'s dropzone
   wrapper). Read each function's existing returned markup and place
   `${errorHtml}` immediately after that field's control(s), still inside
   the same outer wrapper element the function already closes — so the
   error text visually sits with its field, not floating outside the
   field's own box.
3. The functions still do **no validator logic** and **no error-message
   composition** themselves — they only splice in whatever string they're
   handed. When a field has no `validators` in its model, the generator
   passes `''` (or omits the argument, relying on the default), and the
   function must render byte-identical output to what it produces today
   in that case — confirm this explicitly (diff the output for a
   no-validators field before/after this change).
4. Record this signature change plainly in a comment at the top of
   `field-renderers.ts` noting it's a generator-driven addition, so it
   doesn't read as an accidental reintroduction of validator logic to
   someone reading the file later.

### 8.3 — Default error messages, and the validator-key → runtime-error-key map

**Two separate lookups are needed here, and it's important they don't get
merged into one** — they answer different questions:

1. **What text to show** — keyed by our declarative config key
   (`minLength`, `minDate`, etc.), matching the shape the user's example
   uses (`${config.label} is required.` — the field's own label, not a
   generic "this field"):

   ```ts
   export const DEFAULT_VALIDATOR_MESSAGES: Record<string, (label: string, value?: unknown) => string> = {
     required: (label) => `${label} is required.`,
     minLength: (label, value) => `${label} must be at least ${value} characters.`,
     maxLength: (label, value) => `${label} must be at most ${value} characters.`,
     pattern: (label) => `${label} format is invalid.`,
     email: (label) => `${label} must be a valid email address.`,
     min: (label, value) => `${label} must be at least ${value}.`,
     max: (label, value) => `${label} must be at most ${value}.`,
     minDate: (label, value) => `${label} must be on or after ${value}.`,
     maxDate: (label, value) => `${label} must be on or before ${value}.`,
     minRangeDays: (label, value) => `${label} range must be at least ${value} day(s).`,
     maxRangeDays: (label, value) => `${label} range must be at most ${value} day(s).`,
     minSelected: (label, value) => `Select at least ${value} for ${label}.`,
     maxSelected: (label, value) => `Select at most ${value} for ${label}.`,
     requiredTrue: (label) => `${label} must be checked.`,
     maxFileSizeMb: (label, value) => `${label} file must be smaller than ${value} MB.`,
     allowedExtensions: (label, value) => `${label} allowed file types: ${(value as string[]).join(', ')}.`,
     maxFiles: (label, value) => `${label} allows at most ${value} file(s).`,
   };
   ```

   Because Task 1.2's naming rule keeps each key's meaning disjoint
   across families, this stays one flat lookup with no per-type
   branching. Keep it centralized here rather than inlined at each call
   site in `form.ts`, so adding a new validator kind later means touching
   one file, not hunting through the generator.

2. **What string `<hlm-field-error validator="...">` actually needs** —
   Angular's built-in validators don't emit error keys matching our
   config's camelCase naming. `Validators.minLength`/`maxLength` set
   `minlength`/`maxlength` (all lowercase, no camel hump) on the
   control's errors object; `Validators.requiredTrue` sets `required`
   (the same key `Validators.required` uses — a real Angular quirk, not a
   typo). Get this wrong and `hlm-field-error`'s `validator` input will
   never match, and the error silently never shows. Map explicitly:

   ```ts
   export const VALIDATOR_ERROR_KEY_MAP: Record<string, string> = {
     required: 'required',
     minLength: 'minlength',
     maxLength: 'maxlength',
     pattern: 'pattern',
     email: 'email',
     min: 'min',
     max: 'max',
     requiredTrue: 'required', // same runtime key as `required` — deliberate
     // Our own custom validators (Task 8.4.2) control their own error
     // object key, so these map to themselves 1:1:
     minDate: 'minDate',
     maxDate: 'maxDate',
     minRangeDays: 'minRangeDays',
     maxRangeDays: 'maxRangeDays',
     minSelected: 'minSelected',
     maxSelected: 'maxSelected',
     maxFileSizeMb: 'maxFileSizeMb',
     allowedExtensions: 'allowedExtensions',
     maxFiles: 'maxFiles',
   };
   ```

   Confirm the lowercase built-in keys above against Angular's actual
   `ValidatorFn` implementations for the exact version in use (they've
   been stable across Angular versions, but verify rather than trust this
   from memory) before relying on them.

Task 8.4.3's `buildFieldErrorHtml` (below) is the only caller of either
lookup.

### 8.4 — Generator wiring (`form.ts`)

Not every validator key maps to a built-in Angular `Validators.*` call —
Angular ships nothing for date bounds, selection-count bounds, or file
constraints. Two kinds of wiring are needed:

1. **Built-in-backed keys** — `required` → `Validators.required`,
   `minLength`/`maxLength` → `Validators.minLength`/`maxLength`,
   `pattern` → `Validators.pattern`, `email` → `Validators.email`,
   `min`/`max` → `Validators.min`/`max`, `requiredTrue` →
   `Validators.requiredTrue`. The declarative config becomes real
   `Validators` class calls written into generated source, never
   evaluated at generation time — **Task 10 specifies the exact shape
   these calls take in the generated `FormGroup`** (a bare call when a
   control has exactly one validator, an array when it has more — this
   is a real code-generation branch, not a detail to leave to whichever
   way happens to be easiest to template).
2. **Custom-backed keys** — `minDate`/`maxDate`, `minRangeDays`/
   `maxRangeDays`, `minSelected`/`maxSelected`, `maxFileSizeMb`/
   `allowedExtensions`/`maxFiles` have no Angular built-in. Create
   `packages/modules/src/generators/form/lib/custom-validators.ts`
   exporting small validator-factory functions for each (e.g.
   `minDateValidator(min: string): ValidatorFn`,
   `maxSelectedValidator(max: number): ValidatorFn`,
   `maxFileSizeValidator(maxMb: number): ValidatorFn`, operating on
   whatever value shape that field type's control actually holds — check
   each field's underlying control value type before writing its
   validator, e.g. a multi-select control's value is an array, an
   attachment control's value may be a `File[]` or similar). This file
   ships as part of the `form` generator's own `lib/` (copied into the
   generated project alongside the component, the same way
   `field-renderers.ts` is), and the generated component imports from it
   only when a field in the model actually uses one of these keys.
3. **One dedicated function builds the error HTML, per field, not per
   validator kind — now emitting Spartan's `hlm-field-error` shape rather
   than hand-rolled `@if`/`.hasError()` markup.** Per the user's direction,
   each active validator becomes one:

   ```html
   <hlm-field-error validator="required">
     <ng-icon name="lucideCircleAlert" class="me-1 inline size-3.5 align-text-bottom" />
     ${config.label} is required.
   </hlm-field-error>
   ```

   This assumes (per Task 0.5 — **confirm before building this**)
   `hlm-field-error` reads the control's validity/errors ambiently (from
   an ancestor `ControlContainer`/`NgControl` already established by the
   field's own `formControlName`) and manages its own touched/dirty gating
   — so the generated markup does **not** wrap it in a manual
   `@if (form.get(...).invalid && ...touched)` block or call `.hasError()`
   itself; it just declares, for each active validator, which one it's
   for and what to say. If Task 0.5 finds the component actually needs an
   explicit `[control]`/`[formControlName]` input of its own, adjust the
   template below accordingly before building it — don't guess.

   Create `packages/modules/src/generators/form/lib/build-error-html.ts`:

   ```ts
   export function buildFieldErrorHtml(entry: ControlFieldModelEntry): string {
     if (!entry.validators) return '';

     const { label, validators } = entry;

     return Object.entries(validators)
       .map(([key, config]) => {
         const hasMessage = typeof config === 'object' && config !== null && 'message' in config;
         const value = typeof config === 'object' && config !== null ? config.value : config;
         const message = hasMessage && config.message
           ? config.message
           : DEFAULT_VALIDATOR_MESSAGES[key](label, value);
         const runtimeErrorKey = VALIDATOR_ERROR_KEY_MAP[key];

         return `<hlm-field-error validator="${runtimeErrorKey}">
           <ng-icon name="lucideCircleAlert" class="me-1 inline size-3.5 align-text-bottom" />
           ${message}
         </hlm-field-error>`;
       })
       .join('\n');
   }
   ```

   (`ControlFieldModelEntry` here means one of the 15 control variants of
   `FieldModelEntry` — never called for a `ButtonFieldEntry`, which has no
   `validators` to begin with.) One call per field, in Task 3's loop over
   the parsed model, produces that field's whole `errorHtml`. This is the
   single place that:
   - Decides whether a field needs any error markup at all (`validators`
     unset → `''`, so no leftover markup, per Task 8.4.4 below).
   - Loops over that field's *actual* validator keys, not every possible
     key — a `textInput` with only `required` set produces exactly one
     `<hlm-field-error>`, not five.
   - Translates our declarative key to the runtime error key via
     `VALIDATOR_ERROR_KEY_MAP` (Task 8.3) — this is the step that's easy
     to skip and silently break error display, since `minLength` and
     `minlength` look almost identical.
   - Picks a custom message over the default per key.

   A custom `ValidatorFn` (Task 8.4.2) must return its errors object keyed
   by the same runtime name its `VALIDATOR_ERROR_KEY_MAP` entry declares
   (e.g. `{ minDate: true }`) so `validator="minDate"` matches. Confirm
   `lucideCircleAlert` is registered per Task 0.5's icon-registration
   check — don't emit an icon name that isn't wired up.
4. In Task 3's loop over the parsed model, call
   `entry.type === 'button' ? '' : buildFieldErrorHtml(entry)` to get each
   entry's `errorHtml`, then pass it into `renderField(entry, errorHtml)`
   (Task 3.2) to build `fieldsHtml`. For fields with no `validators`,
   `buildFieldErrorHtml` already returns `''` — don't special-case that
   again at the call site; there should be no leftover markup at all for
   a validator-free field.
5. Import `Validators` from `@angular/forms`, and/or from
   `custom-validators.ts`, in the generated `.ts` only when at least one
   field in the model actually needs that import — keep this consistent
   with the existing only-import-what's-used rule from Task 3.2. Track
   built-in and custom imports separately, since a model using only
   `required`/`minLength` needs no `custom-validators.ts` import at all.

### 9.1 — Handler name safety rule

  clear error if a `handler` matches one of these.
- **Two buttons may share the same `handler` name deliberately** (e.g.

```ts
  name: ['', Validators.required],
  email: ['', [Validators.required, Validators.email]],
  age: [0, [Validators.required, Validators.min(18)]],
  isActive: [true],
});
```

Three things this locks in that weren't fully pinned down before:
`NonNullableFormBuilder` usage, a per-control tuple of
`[initialValue, validators?]`, and — critically — **a bare validator call
when there's exactly one, an array only when there's more than one**.
This directly answers "make sure validators are actually added to the
generated form controls" — Task 8.4 built the pieces (which `Validators.*`
calls, which custom validators); this task is where they're assembled
into the real `FormGroup`, so a model with validators produces a
`FormGroup` where those validators are actually attached, not just
computed and discarded.

### 10.1 — Component injects `FormBuilder`

```ts
private readonly fb = inject(FormBuilder);
```

Match this workspace's existing DI convention — `inject()`, not
constructor injection, consistent with how other generated/hand-written
components in this codebase already do it (e.g. `HlmButton`'s
`injectBrnButtonConfig()`). Import `FormBuilder` from `@angular/forms`
unconditionally (every generated form needs it, unlike `Validators` or
`custom-validators.ts`, which are only-imported-when-used per Task 3.2/
Task 8.4.5).

### 10.2 — Per-control initial value

`FieldModelEntry` currently has no `defaultValue` — this needs adding.
Add to `BaseControlEntry` (Task 1.2.a):

```ts
interface BaseControlEntry extends BaseEntryLayout {
  formControlName: string;
  defaultValue?: string | number | boolean | string[] | null;
}
```

This is deliberately a single loosely-typed optional property rather than
routed through a per-family mapped type like `FieldValidatorsMap` —
`defaultValue` is scaffolding convenience, not a correctness fence the
way validators are, so a lightweight runtime check is proportionate:

- In `parseFieldModel` (Task 2), if `defaultValue` is present, read it as
  a literal and do a `typeof`-level sanity check against the field's
  family (e.g. reject a string `defaultValue` on a `numberInput`, reject
  a non-array `defaultValue` on `selectMultiple`/`comboboxMultiple`) —
  throw a clear error naming the field and the mismatch if it fails.
- When `defaultValue` is omitted, the generator supplies a per-`FieldType`
  fallback:

  | Field type family | Fallback default |
  |---|---|
  | `textInput`, `inputOtp`, `select`, `combobox`, `radioGroup` | `''` |
  | `numberInput`, `slider` | `0` |
  | `switchToggle`, `checkbox` | `false` |
  | `datePicker`, `timePicker`, `dateRangePicker` | `null` |
  | `selectMultiple`, `comboboxMultiple` | `[]` |
  | `attachment` | `null` |

  Centralize this table in `field-model.types.ts` or a small sibling file
  next to `VALID_VALIDATOR_KEYS` — same "one place to update" reasoning.

### 10.3 — Per-control validators expression: bare vs. array

Add a function (near `buildFieldErrorHtml`, e.g. in a
`lib/build-control-validators.ts`) that returns the **source text** for a
control's validators argument — not a runtime value, since this text is
spliced into generated `.ts` source:

```ts
export function buildControlValidatorsExpression(entry: ControlFieldModelEntry): string | null {
  if (!entry.validators) return null;

  const expressions = Object.entries(entry.validators).map(([key, config]) =>
    buildSingleValidatorExpression(key, config), // e.g. 'Validators.min(18)', or a custom-validators.ts call
  );

  if (expressions.length === 0) return null;
  if (expressions.length === 1) return expressions[0];
  return `[${expressions.join(', ')}]`;
}
```

`buildSingleValidatorExpression` is where Task 8.4.1/8.4.2's built-in vs.
custom split actually gets turned into source text (e.g. `'min'` →
`` `Validators.min(${value})` ``, `'minDate'` →
`` `minDateValidator(${JSON.stringify(value)})` ``). Then, per control in
the `FormGroup` object literal:

```ts
`${entry.formControlName}: [${formatDefaultValue(entry)}${
  buildControlValidatorsExpression(entry) ? `, ${buildControlValidatorsExpression(entry)}` : ''
}]`
```

producing exactly the shape in the user's example: `name: ['',
Validators.required]` (one validator, bare), `email: ['', [Validators.required,
Validators.email]]` (two, array), `isActive: [true]` (none, no second tuple
element at all — not even an empty array).

### 10.4 — Testing addition (extends Task 6)

- Re-generate the sample form (with the validator-bearing fields from
  Task 8.5) and inspect the actual generated `<name>.ts` `form` property
  literally, confirming:
  - It's built via `this.fb.nonNullable.group({...})`, not `new FormGroup()`
    or a plain (nullable) `FormBuilder`.
  - A control with exactly one validator has a bare validator reference,
    not a one-element array.
  - A control with multiple validators has an array, in the same order
    the model declared them.
  - A control with no `validators` has a single-element tuple (default
    value only) — no trailing `undefined`/`[]`.
  - Default values match Task 10.2's table for fields that didn't specify
    `defaultValue`, and match the model's explicit value where they did.
  - A `defaultValue` of the wrong shape for its field's family (e.g. a
    string on a `numberInput`) throws a clear error end-to-end.

## Further Recommendations (outside the task list proper)

A few things worth deciding on explicitly, not urgent blockers:

1. **Package placement.** This generator's actual behavior (compose a
   component from a config file using pre-built render functions) is
   closer in spirit to what `components:ui` generators do than to the
   `modules:*` generators (auth/rbac/user-management), which all add
   routes/nav/services around a feature. Worth a deliberate decision on
   whether `form` belongs under `packages/components` instead of
   `packages/modules` — I'd lean towards leaving it under `modules` for
   now since that's where the user asked for it and it avoids a
   cross-package move later if it grows feature-ish behavior (e.g.
   submit-handling wiring), but flagging it since the shape doesn't fully
   match its neighbors.
2. **A `--list` flag** (or equivalent) that just prints the 16 supported
   `FieldType` values and exits, so developers authoring `bp.models` files
   don't have to go read `field-model.types.ts` to know their options.
   Cheap to add, meaningfully improves the authoring experience.
3. **Treat `FieldModelEntry` as a real, tested deliverable.** Since
   developers will hand-author files against this type, it's worth a
   small typecheck-only test file (a `bp.models` fixture that intentionally
   uses every `FieldType` once) that's compiled as part of CI, so a future
   accidental shape change to `FieldModelEntry` or the renderer map is
   caught at build time rather than discovered by a developer at
   generate-time.
4. **A generated-file header comment.** Since option data sources are
   still explicitly deferred (validators no longer are, as of Task 8),
   consider having the generator prepend a short comment block to the
   generated `.ts` (or `.html`) file noting that real option/data sources
   still need to be added before production use. Costs nothing to add and
   reduces the chance this gets shipped as-is by mistake.
5. **Custom validator functions (v2).** Task 8's `validators` config only
   covers Angular's built-in validators. A real "matches another field"
   or "checks against an async service" validator isn't safely expressible
   as a primitive literal. If that's needed later, the safe shape is
   almost certainly reference-by-name rather than reference-by-expression
   — e.g. `validators: { custom: 'matchesConfirmPassword' }`, resolved by
   the generator against a conventionally-named file (say
   `bp.models/validators.ts`) it knows to import from, rather than trying
   to parse or execute an arbitrary function body out of the model file.
   Worth deciding on that convention explicitly if/when the need shows up
   — not something to guess at now.
6. **No built-in "submit" convenience (v2 candidate).** Right now every
   button, including a form's actual submit action, needs an explicit
   `handler` the developer implements by hand (e.g. reading `form.value`
   themselves). That's consistent with today's ask — explicit handler
   names, no magic — but if most generated forms end up hand-writing the
   same three lines of "guard `form.invalid`, read `form.value`, call
   something," a later, opt-in shorthand (e.g. a reserved `handler:
   '$submit'` that the generator recognizes and wires directly to
   `form.value` without a stub) could remove real boilerplate. Not
   something to build speculatively now — worth revisiting once a few
   real forms have been generated and the repetition (or lack of it) is
   visible.
